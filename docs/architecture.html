Factory Inventory Management

A Vue 3 single-page app talks to a FastAPI server over plain HTTP. The server keeps every record in memory, loaded once from seven JSON files. There is no database, no authentication, and nothing is ever written back.

Architecture

Two processes on one machine. The browser holds all UI state; the Python process holds all data.

Request flow

What happens when someone picks Tokyo in the Warehouse filter while on the Overview page.

  1. The Warehouse <select> is bound with v-model to selectedLocation, a ref declared at module level in useFilters.js. Every view that calls useFilters() gets the same ref. FilterBar.vue:26

  2. Dashboard watches all four filter refs, so the change triggers loadData(). Dashboard.vue:676

  3. loadData() sets loading = true and calls getCurrentFilters(), which returns { warehouse: 'Tokyo', category: 'all', status: 'all' }. A month key is added only when a time period is chosen. useFilters.js:27

  4. Promise.all fires four calls at once: dashboard summary, orders, inventory and backlog. Dashboard.vue:561

  5. api.js builds the query string with URLSearchParams and leaves out every value equal to 'all', so only ?warehouse=Tokyo goes over the wire, straight to port 8001. Backlog is fetched with no parameters. api.js:6

  6. Each handler runs apply_filters. Warehouse is an exact, case-sensitive match; category and status ignore case. The orders and summary handlers also run filter_by_month. main.py:33

  7. The result is a slice of the in-memory lists. Tokyo holds 9 of the 32 inventory items.

  8. Orders, inventory and backlog are checked against Pydantic response models on the way out. The dashboard summary is returned as a plain dict.

  9. response.data is stored in refs: summary, allOrders, inventoryItems and the backlog list.

  10. Computed properties such as statusData, categoryData and topProducts recalculate, and the page re-renders.

Hand-rolled instead

Shared state lives in three composables: useFilters, useI18n (English and Japanese, choice saved in localStorage, yen at a fixed 150 per dollar) and useAuth (a mock user who is always signed in). Charts are CSS-sized bars plus one SVG donut on the Overview page.

Known gaps

Places where the code does something a newcomer would not expect, or where the docs and the code disagree.

  • Broken

    Task actions call endpoints that don't exist

    App.vue loads, adds, toggles and deletes tasks through /api/tasks. The server has no such route, so each call returns 404 and is only logged to the console.

  • Broken

    Create PO renders a component that doesn't exist

    Dashboard.vue:289 uses <PurchaseOrderModal>, which is never imported and has no file. The button also checks purchase_order_id while the server sends has_purchase_order.

  • Data

    Shortages table empties under any warehouse or category filter

    None of the 4 backlog SKUs exist in inventory.json, and the Overview keeps a backlog row only if its SKU is in the filtered inventory.

  • Data

    Most demand forecasts point at unknown SKUs

    8 of the 9 forecast SKUs are missing from inventory. Only PSU-501 can survive a warehouse or category filter on the Demand page.

  • Data

    Order IDs 201 to 210 appear twice

    orders.json has 250 records but 240 unique IDs.

  • Code

    Four of five Overview KPIs are hardcoded

    Inventory turnover, orders fulfilled, fill rate and processing time are fixed numbers. Only revenue comes from /api/dashboard/summary.

  • Code

    Reports bypasses the shared patterns

    Reports.vue uses the Options API, calls axios with hardcoded URLs instead of api.js, ignores the filters and has no translations.

  • Code

    Backlog.vue is unreachable

    It has no route and nothing imports it. Backlog data appears only in the Overview shortages table.

  • Docs

    Filters do not apply to all data

    CLAUDE.md and the README say all four filters apply everywhere. Only /api/orders and /api/dashboard/summary accept all four; see the table above for the rest.

  • Docs

    Test docs overcount

    The test README claims 51 to 55 tests and lists a test_orders.py. There are 40 tests in three files, and none cover orders or reports.
